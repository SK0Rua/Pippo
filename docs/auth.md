# Реєстрація, вхід і сесії

## Реєстрація — `POST /api/auth/register`

```json
{ "username": "valik", "password": "secret123", "timezone": "Europe/Kyiv" }
```

Що відбувається:

1. **Перевірка імені:** `3–24` символи, літери (будь-якої мови), цифри, `_`, `.`, `-`.
   Регулярка `^[\p{L}\p{N}_.-]{3,24}$`, тож «Олена_2» — дозволене ім'я.
2. **Перевірка пароля:** від 6 до 200 символів. Вимог до великих літер і цифр немає навмисне:
   довжина захищає краще, ніж складні правила, які люди обходять через `Password1!`.
3. **Зайняте ім'я** → `409`. Порівняння без урахування регістру (`COLLATE NOCASE`),
   тож «Valik» і «valik» — та сама людина.
4. **Часовий пояс** береться з браузера (`Intl.DateTimeFormat().resolvedOptions().timeZone`)
   і перевіряється через `Intl`. Невідомий → `Europe/Kyiv`. Від нього залежить, коли настає
   «новий день» для серії та лімітів.
5. Однією транзакцією створюються: користувач, словник «Мій словник», стартові 50 🌾,
   а якщо ім'я є в `PIPPO_ADMIN` — ознака адміністратора.
6. Одразу видається сесія, тож окремий вхід не потрібен.

Пошти ми не збираємо взагалі. Наслідок: **відновити забутий пароль неможливо** — це свідомий
компроміс на користь простоти, який доведеться скасувати, якщо Pippo стане не лише твоїм.

## Як зберігається пароль

```js
const salt = crypto.randomBytes(16);
const hash = crypto.scryptSync(password, salt, 64);
return `${salt.toString('hex')}:${hash.toString('hex')}`;
```

- **scrypt** — повільна функція, стійка до підбору на відеокартах. Вбудована в Node, без залежностей.
- **Сіль на кожного користувача** — однакові паролі дають різні хеші.
- Зберігається рядок `сіль:хеш`; самого пароля немає ніде.
- Перевірка — `crypto.timingSafeEqual`, щоб час відповіді не підказував, наскільки хеш «майже збігся».

## Вхід — `POST /api/auth/login`

```json
{ "username": "valik", "password": "secret123" }
```

- Помилка завжди однакова: **«Невірне ім'я або пароль»**, `401`. Так не видно, чи існує акаунт.
- Перед видачею нової сесії прибираються протерміновані сесії цього користувача.
- Успіх → нова сесія (стара на іншому пристрої лишається робочою).

## Сесії

```js
const token = crypto.randomBytes(32).toString('hex');   // 256 біт
db.prepare('INSERT INTO sessions (token, user_id, expires) VALUES (?, ?, ?)')...
res.setHeader('Set-Cookie',
  `pippo_sid=${token}; HttpOnly; SameSite=Lax; Path=/; Max-Age=2592000` + (production ? '; Secure' : ''));
```

| Властивість | Навіщо |
| --- | --- |
| `HttpOnly` | JavaScript сторінки не може прочитати токен — крадіжка через XSS не працює |
| `SameSite=Lax` | чужий сайт не зробить запит від твого імені (захист від CSRF) |
| `Secure` (у production) | cookie не піде відкритим HTTP |
| `Max-Age` 30 днів | і в базі, і в cookie; протерміновані сесії не проходять перевірку |

Токен — не JWT, а випадковий рядок із записом у базі. Тому **вихід справді працює**:
`POST /api/auth/logout` видаляє рядок, і токен миттєво стає марним.

Перевірка на кожному запиті (`auth`):

```sql
SELECT u.* FROM sessions s JOIN users u ON u.id = s.user_id
WHERE s.token = ? AND s.expires > ?
```

Немає сесії → `401`. Клієнт на `401` сам перекидає на екран входу.

## Ще два захисти

**Обмеження спроб.** `/auth/register` і `/auth/login` пропускають 30 запитів з IP за 15 хвилин,
далі `429`. Лічильник у пам'яті процесу — перезапуск його обнуляє.

**Тільки JSON.** Будь-який змінювальний запит до `/api/*` без `content-type: application/json`
отримує `415`. Звичайна HTML-форма з чужого сайту так надіслати не може, тож це другий рубіж
проти CSRF після `SameSite`.

## Хто такий адмін

Список імен у `.env`: `PIPPO_ADMIN=valik,demo`. Позначка ставиться при старті сервера
й при реєстрації такого імені. Сторінка `#/admin` і `/api/admin/stats` перевіряють прапорець
на сервері — приховати кнопку в інтерфейсі замало.

## Чого поки немає

- відновлення пароля (немає пошти);
- зміни пароля;
- двофакторної автентифікації;
- списку активних сесій і кнопки «вийти всюди»;
- токенів для зовнішніх клієнтів — саме їх бракує для браузерного розширення,
  бо cookie з `SameSite=Lax` розширенню не дістанеться.

## Тести

У `npm test` авторизацію покривають: зайняте ім'я, короткий пароль, невірний пароль,
доступ без входу до закритих даних, відмова на не-JSON, ізоляція чужих даних,
доступ до адмінки для звичайного користувача.
